# 02 — 系統架構設計

> 個股網路溫度系統（Stock Heat）— 設計文件 2/7
> 版本：v0.1 ｜ 最後更新：2026-06-29

## 1. 架構總覽

採用**分層 + 管線（pipeline）**架構，資料由左（外部來源）流向右（使用者）：

```
┌──────────────┐   ┌──────────────┐   ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
│  資料來源層   │ → │   擷取層      │ → │   處理層      │ → │   計算/儲存層 │ → │   服務/呈現層 │
│  Sources     │   │  Ingestion   │   │  Processing  │   │  Compute/DB  │   │  API / UI    │
└──────────────┘   └──────────────┘   └──────────────┘   └──────────────┘   └──────────────┘
  新聞/論壇/社群       擷取器plugins      斷詞/個股辨識/        溫度演算法/        REST API/
  Google Trends      排程+佇列          情緒分析           時序資料庫         儀表板
```

## 2. 分層職責

### 2.1 資料來源層（Sources）
外部網站與 API：財經新聞網、PTT、財經論壇、Google Trends、（後續）社群平台。詳見 [03](03-資料來源與擷取設計.md)。

### 2.2 擷取層（Ingestion）
- 每個來源實作一個 **Collector plugin**，遵守共同介面 `BaseCollector`。
- **排程器**（APScheduler，後續可換 Celery beat）依各來源頻率觸發。
- 抓回的原始內容送入**訊息佇列**（Redis Stream / 後續 RabbitMQ），與處理層解耦。
- 原始內容寫入 `raw_documents`（原文分層，供重算）。

### 2.3 處理層（Processing）
針對每則文件依序執行：
1. **清洗**：去 HTML、正規化、語言判定。
2. **去重**：URL 正規化 + SimHash 近似去重。
3. **斷詞與關鍵詞**：jieba（自訂金融詞典）/ 後續 CKIP。
4. **個股辨識（NER + 別名消歧）**：把文件關聯到 0..N 檔個股，附信心分數。
5. **情緒分析**：規則詞典打底 → 領域模型，輸出 -1~+1。
產出寫入 `processed_documents` 與 `document_ticker_mentions`。

### 2.4 計算/儲存層（Compute/Storage）
- **溫度計算器**：以視窗（日/盤中）聚合每檔個股的聲量、情緒、來源權重、時間衰減 → Heat Score。詳見 [04](04-溫度演算法設計.md)。
- 儲存於時序表 `ticker_heat_timeseries`（PostgreSQL + TimescaleDB）。
- **Redis** 作為佇列、快取（榜單、熱門個股）。

### 2.5 服務/呈現層（API/UI）
- **FastAPI** 提供 REST API（榜單、個股詳情、時序、搜尋）。詳見 [06](06-API與後端服務設計.md)。
- **Next.js** 儀表板呈現榜單與圖表。詳見 [07](07-前端儀表板與部署維運.md)。

## 3. 技術選型

| 層 | 技術 | 理由 |
|----|------|------|
| 語言 | Python 3.11 | 擷取/NLP/資料生態完整 |
| 擷取 | requests / httpx + selectolax / feedparser | 輕量、適合新聞 RSS 與 HTML |
| 排程 | APScheduler（MVP）→ Celery | MVP 單機即可，之後水平擴充 |
| 佇列/快取 | Redis | 佇列、去重、榜單快取一站搞定 |
| 主資料庫 | PostgreSQL 16 + TimescaleDB | 關聯 + 時序兼顧 |
| NLP | jieba + 自訂詞典；情緒詞典 → FinBERT-zh（後續） | 漸進式，先可用再求準 |
| 後端 API | FastAPI + Pydantic v2 | 型別清楚、自動文件 |
| 前端 | Next.js 14 + Recharts | SSR + 圖表 |
| 部署 | Docker Compose（MVP）→ K8s | 漸進 |

## 5. 資料流（以財經新聞為例）

1. Scheduler 每 5 分鐘觸發 `NewsCollector`。
2. Collector 讀取各新聞來源 RSS/列表 → 取得文章 URL 清單。
3. 對未見過的 URL 抓取全文，產生 `RawDocument`，push 到 `ingest.raw`。
4. Processing Worker 消費：清洗 → 去重 → 斷詞 → 個股辨識 → 情緒 → 寫入 DB。
5. Heat Compute Job 每 15 分鐘／每日聚合 → 更新 `ticker_heat_timeseries`、刷新榜單快取。
6. API 讀取，UI 呈現。

## 6. 部署拓樸（MVP）

單機 Docker Compose：`api`、`worker`、`scheduler`、`postgres`、`redis`、`web`。
水平擴充時，`worker` 可多副本（佇列天然分流），`api` 無狀態可多副本，DB 採讀寫分離。詳見 [07](07-前端儀表板與部署維運.md)。

## 7. 跨切面（Cross-cutting）

- **設定**：以環境變數 + `pydantic-settings` 管理；來源設定走 `config/sources.yaml`。
- **日誌**：結構化 JSON log（structlog）。
- **監控**：Prometheus 指標（抓取量、佇列長度、處理延遲、錯誤率）。
- **重算**：raw 與 derived 分層 → 改演算法後可 replay。
